## M0 构建环境与骨架（2026-09-20）

### 环境事实（实测）

| 项 | 结果 |
|---|---|
| JDK 17 | `C:\jdk17` = Oracle JDK 17.0.19+9-LTS，含 `jpackage` / `jlink` / `jmods` |
| JDK 8 | `C:\jdk-1.8`，**`JAVA_HOME` 默认指向它** |
| Maven | PATH 无；IntelliJ 内置 3.9.16；本项目自带 3.9.9 |
| JavaFX | 选定 17.0.13（LTS） |

### 坑 1：XML 注释里不能出现连续两个短横线

```
[FATAL] Non-parseable POM ...: in comment after two dashes (--) next character must be > not m
```
**原因**：在 `<build>` 上方写了 `<!-- ... jpackage 的 --main-jar 参数 ... -->`。
XML 规范禁止注释内容包含 `--`。

**规避**：pom 注释里不要写命令行参数原文，改成 "main-jar 参数" 或加空格拆开。

### 坑 2：JavaFX 在 Maven 上必须显式带 classifier

**实测证据**（Maven Central 的 `Content-Length`）：

| 制品 | 大小 |
|---|---|
| `javafx-base-17.0.13.jar` | **302 字节** |
| `javafx-base-17.0.13-win.jar` | 746,012 字节 |
| `javafx-graphics-17.0.13.jar` | **306 字节** |
| `javafx-graphics-17.0.13-win.jar` | 5,910,927 字节 |

解包 `javafx-base-17.0.13.jar` 后只有一个 `META-INF/MANIFEST.MF`（66 字节），
**没有 class，也没有 module-info**。真正的 class 与原生 dll 全在 `-win` 分类包里。

**规避**：4 个 JavaFX 模块全部显式声明 `<classifier>win</classifier>`。
因为本项目非目标即跨平台，固定 win 是清晰的取舍。

### 坑 3：`copy-dependencies` 会把空包一并拷进 module-path，导致模块重名

即使依赖显式带了 classifier，JavaFX 各模块的 POM 仍会把「无 classifier 空包」作为**传递依赖**再拉一遍。
空包无 module-info，会被 module-path 当成自动模块 `javafx.base` / `javafx.graphics`，
与真实模块同名冲突（`Two versions of module javafx.base found`）。

**规避**：`target/javafx` 的 `copy-dependencies` 执行加 `<excludeTransitive>true</excludeTransitive>`，
只拷 4 个直接声明的 `-win` 包。修好后目录内恰好 4 个 jar，已核对。

### 坑 4：`~/.m2` 在本环境不可写

```
java.io.FileNotFoundException: C:\Users\<用户名>\.m2\repository\...\_remote.repositories (拒绝访问。)
```
**原因**：全局仓库在工作区之外。更深层的原因是本机全局仓库**本来就有问题**——
`~/.m2/setting.xml` 文件名少了个 s（应为 `settings.xml`），所以从未生效；
而它内部还把 `localRepository` 指向了不存在的 `C:\Users\Administrator\.m2\repository`。
（这个文件我们没动，属于用户既有环境。）

**规避**：`scripts/mvn.cmd` 用 `-Dmaven.repo.local=<项目>\tools\m2repo`。
额外好处：依赖集随工程走，构建完全自包含、可复现，不污染本机。

### 坑 5：`.cmd` 脚本里绝对不能出现非 ASCII 字符（**最容易复发**）

**症状**：脚本执行到一半开始报一堆荒谬错误——
`'e' is not recognized`、`'cp' is not recognized`、`'el.jar" (' is not recognized`。

**原因**：脚本开头有 `chcp 65001`。cmd.exe 按**字节偏移**跟踪自己在批处理文件里的读取位置，
代码页在读取中途被切换后偏移量失效，解析器从**某一行中间**继续执行，于是把
`-Djavafx.cachedir="..."` 之类的片段当命令执行。

**规避**：本项目所有 `.cmd` 一律**纯 ASCII**（注释也写英文），已加校验。
需要写中文说明就写到 `docs/` 里。
> 校验命令（新增脚本后跑一次）：统计脚本内大于 127 的字节数，必须为 0。

### 坑 6：JavaFX 原生库缓存目录不可写时会刷屏

**症状**：`Can not create cache at C:\Users\<用户名>\.openjfx\cache\17.0.13` 反复打印约 50 行。

**原因**：JavaFX 会把 jar 内的原生 dll 解压到 `%USERPROFILE%\.openjfx\cache\<version>`；
该目录本环境不可写，JavaFX 退化为临时目录继续工作，但每次查找都打印一行警告。

**规避**：开发与自检时用 `-Djavafx.cachedir=<项目>\target\jfxcache`。
普通用户机器上 `%USERPROFILE%` 可写，不会有此问题。

### 坑 7：JavaFX 版本号只能从 jar 文件名拿到

**实测证据**：
- `java --describe-module javafx.graphics` 输出中**没有版本号**；
- `javafx-graphics-17.0.13-win.jar` 的 MANIFEST 只有 `Manifest-Version: 1.0`，
  没有 `Implementation-Version`；
- `System.getProperty("javafx.runtime.version")` 为空。

**结论**：`ModuleDescriptor.version()`、MANIFEST、系统属性三条路都拿不到版本，
唯一带版本号的是 **jar 文件名**。

**规避**：`MainApp.detectJavaFxVersion()` 以「加载来源 jar 的文件名」为主来源（正则取版本号），
并把 jar 文件名一起显示。这不只是好看——M6 在**没有装 Java 的机器**上验证免装分发时，
需要靠这行输出证明「加载的确实是随包自带的那份 JavaFX」。

## M1 扫描核心与文件表格（2026-09-20）

### 坑 8：TableView 接 SortedList 时必须显式绑定 comparator（**最隐蔽的一个**）

**症状**：表格数据全对、表头也画出了"已按名称升序"的箭头，**但行序是扫描顺序，根本没排序**。
数据和界面看上去都正常，只有逐行核对顺序才能发现。

**顺带一提**：我先怀疑是 `Collator` 排错了，用 jshell 直接问了一遍——
`Collator.getInstance(Locale.CHINA)` 与 `String.CASE_INSENSITIVE_ORDER` 对这批文件名给出的顺序完全一致，
且 `compare(x,x)==0` 全部成立。**排序器没问题，是没接上。** 先测量再改，省下了一次瞎改。

**根因**：JavaFX 不会自动把 TableView 的排序作用到 SortedList 上，运行时自己打了日志：

```
信息: TableView items list is a SortedList, but the SortedList comparator should be
bound to the TableView comparator for sorting to be enabled
(e.g. sortedList.comparatorProperty().bind(tableView.comparatorProperty());).
```

**规避**：三步都要做，且顺序不能错：
```java
sortedItems.comparatorProperty().bind(table.comparatorProperty());  // 1. 绑定
table.setItems(sortedItems);                                        // 2. 接数据
table.applyDefaultSort();   // 3. clear 再 setAll(sortOrder) 强制产生一次变更事件
```
`applyDefaultSort` 内部先 `getSortOrder().clear()` 再 `setAll(col)`：若 sortOrder 内容没变，
不 clear 就不会触发变更事件，比较器也就不会被推送。

**回归防线**：`--ui-selftest` 里加了一条顺序断言，逐行比较相邻两行的名称，
一旦顺序不是升序就直接失败。这类 bug 不断言顺序是抓不到的。

### 坑 9：`--screenshot` 让"界面长什么样"也能自动留证

踩到坑 8 靠的不是单元测试——单元测试全绿。靠的是把界面**渲染成 PNG 再看**。
所以把截图做成了应用自带模式（`Scene.snapshot` + `PixelReader` 手写 PNG）：

- 不用 `SwingFXUtils`：那需要额外引入 `javafx.swing` 模块，为一行像素搬运不值当
- 不用操作系统级截屏：本机 pwsh 7 缺 `System.Drawing.Common`，且截屏会被窗口遮挡影响
- `Scene.snapshot` 渲染的就是 JavaFX 自己的合成结果，正是要验证的东西

**读图读不准的地方要用文本核对。** 我一度以为"所在位置"列把 `/` 显示成了 `\`，
jshell 验证 `replace('\\','/')` 结果正确后，改成在自检里**直接打印单元格字符串**，
一眼确认是 `某项目/collector`。小字号下 `/` 与 `\` 在截图里几乎无法区分。

### 脚本重构：抽公共启动器 `_java.cmd`

到 M1 时已有 4 个脚本要跑同一段 java 命令（含 module-path / classpath / 缓存目录参数），
复制 4 份必然出现"改了一处漏三处"。抽出 `scripts\_java.cmd`，
`run/scan/selftest/uiselftest/screenshot` 各自只负责解析参数再转调它。
**关键收益**：那段 java 命令与 M6 的 jpackage 产物结构**完全一致**，
所以开发期跑通就等于验证了打包后的接线方式。

## M2 搜索 / 筛选 / 分类侧栏（2026-09-20）

### 坑 10：`CONSTRAINED_RESIZE_POLICY` 会无视 prefWidth，把各列压成一样宽

**症状**：6 列各占 152px。名称列只能显示四五个汉字（"作业区地理…"），
而"大小"列白白空着一大片。我是在检查落盘的 `config.json` 时才发现的：

```json
"columns": [
  { "id": "name",     "width": 152.0 },
  { "id": "type",     "width": 152.0 },
  { "id": "size",     "width": 152.0 },
  { "id": "location", "width": 152.0 },
  { "id": "created",  "width": 153.0 },
  { "id": "modified", "width": 152.0 }
]
```
六个数字几乎完全相同——这不是"我设的宽度生效了"，而是"我的设置被忽略了"。

**根因**：JavaFX 的 `CONSTRAINED_RESIZE_POLICY` 把可用宽度在<b>所有列之间均分</b>，
不参考 `prefWidth`。它的设计目标是"永远填满、永不出现横向滚动条"，代价是放弃列宽比例。

**规避**：改用默认的 `UNCONSTRAINED_RESIZE_POLICY`，让 `prefWidth` 生效，
再自己把剩余宽度补给名称列（`stretchNameColumn()`），兼顾了比例与"右侧不留空白"。

### 坑 11：自己算弹性列宽时，忘了纵向滚动条会吃掉宽度

**症状**：改成 UNCONSTRAINED + 自己拉伸后，底部冒出一条横向滚动条。

**根因**：`TableView.getWidth()` 是整表宽度，而列可用宽度还要减去纵向滚动条与边框。
我最初只预留了 4px，列总宽刚好超出视口约 13px，于是横向滚动条出现，
而滚动条一出现又改变可用高度、影响是否需要纵向滚动条——很容易演变成布局抖动。

**规避**：预留 20px（`LAYOUT_RESERVE`），并用 `stretchingNameColumn` 布尔量防止
"设置列宽 → 触发布局 → 再次设置列宽"的回环。

### 坑 12：`ObservableList.setAll(E...)` 是 varargs，通配泛型会触发 unchecked 警告

**症状**：`getSortOrder().setAll(col)` 报
"对于类型为 `TableColumn<FileItem,?>[]` 的 varargs 参数, 泛型数组创建未经过检查"。

**规避**：换成非 varargs 的 `Collections.singletonList(col)`。
另外在 pom 里<b>常驻</b>了 `-Xlint:unchecked`，让这类警告在构建期就必须处理掉，
而不是靠"这次没看见"。

### 关于"用像素读数字"的教训

M2 的验收截图上，我一度以为侧栏分类计数之和（134）超过了总数（112），
怀疑有重复计数。但那个数字是我从一张被缩放到 1049px 宽的截图里"读"出来的，
而实际值是 112——我把 `22` 看成了 `44`。

**结论**：凡是能用文本断言的，绝不用眼睛看截图。因此给 `--ui-selftest` 加了
**划分不变式**断言：各类型分类计数之和必须等于"全部"。
逐项比对"计数 == 点进去的行数"是不够的——若同一项被算进两个分类，
每个分类单独看都自洽，只有总和能暴露问题。

### 侧栏设计的一个刻意的取舍

侧栏计数来自<b>搜索结果</b>而不是全量数据，因此搜索 `type:image` 时
其余分类会全部显示 0。这样做的理由是：用户能一眼看出"当前这批结果的类型分布"，
而不是永远看到与当前视图无关的全量统计。分类列表本身则不随搜索变化
（只收录数量大于 0 的类型），避免每敲一个字符侧栏就跳一次、鼠标还没移过去目标就没了。

## M3 打开 / 定位 / 重命名 / 删除到回收站（2026-09-20）

### 坑 13：`Path.equals` 在 Windows 上**忽略大小写**（静默失效的真 bug）

**症状**：把 `readme.md` 重命名为 `README.md`，界面报告"已重命名为 README.md"，
**文件却纹丝不动**。没有任何异常、没有任何提示。

**根因**：`RenameService.rename()` 里先做了"名字没变就直接返回成功"的短路：
```java
if (source.equals(target)) {                      // readme.md vs README.md
    return new Result(true, source, false, "");   // Windows 上这里会命中！
}
boolean caseOnly = isCaseOnlyChange(source, newName);
```
Windows 的 `WindowsPath.equals` 是大小写不敏感的，所以"仅大小写变化"这条路
**永远走不到**——它在前面就被当成"没有变化"短路掉了。

**规避**：先算 `caseOnly`，再决定要不要短路：
```java
boolean caseOnly = isCaseOnlyChange(source, newName);
if (source.equals(target) && !caseOnly) { ... }
```

**教训**：这是"只在 Windows 上出现、且不报错"的典型缺陷。它是被
`assertTrue(result.caseOnlyChange())` 这条断言抓出来的——如果测试只断言
`result.success()`，就会一路绿着把 bug 放过去。

### 坑 14：Shell 报告成功 ≠ 文件进了回收站（**本里程碑最重要的发现**）

**症状**：`SHFileOperationW` 返回 0（成功），文件确实从原位置消失，
但回收站条目数**没有增加**——也就是文件其实被永久删除了。

**排查过程**（每一步都是为了排除自己而不是猜）：
1. 用 `SHQueryRecycleBin` 取条目数，前后对比 → 确认没有增加
2. 直接翻 `C:\$Recycle.Bin\<SID>\` 里的 `$I` 元数据文件（里面存着原始路径）→ 没有我们的文件
3. 查注册表 `BitBucket\Volume\{...}` → `NukeOnDelete=0`，回收站**没有被关闭**，配额 50GB
4. 打印 `SHFILEOPSTRUCTW` 的字段偏移 → size=56、`fFlags` 在偏移 32、值 `0x4654`
   确实包含 `FOF_ALLOWUNDO`，**绑定没有错**
5. 对比五组不同标志位（含"只用 ALLOWUNDO"和"完全不带 ALLOWUNDO"的对照组）→
   **行为完全一致**，说明与标志位无关

**结论**：运行环境阻止了 Shell 写入 `C:\$Recycle.Bin`（该路径在工作区之外）。
本沙箱环境内无法验证真机回收站行为。

> **后续（2026-09-20 17:09，已闭环）**：在真机上用界面删除 `临时文件.txt` 后，
> 系统回收站里确实有它（原位置、删除时间都正确），**且没有触发下面的告警**——
> 说明调用参数正确，兜底判定也没有误报。详见本文件 M3 段的证据表。

**已转化为产品能力**：不能只信 API 的返回码。`DeleteService` 现在会在删除后
用条目数前后差做验证，发现"报告成功但未进入回收站"就单独告警：

> "N 项已删除，但未能确认它们进入了回收站……很可能已被【永久删除】，无法从回收站还原。"

**判定刻意宽松**：只在条目数**完全没有增加**时才判为可疑。
严格比较"增加量 == 条目数"会把"同时有别的程序清空回收站"误报成失败，
而误报会让用户对提示失去信任。

**为了让这段逻辑可测**：把"调用 Shell"与"查询条目数"抽成两个可注入的接缝
（`RecycleAction` / `RecycleBinProbe`），测试用假实现即可覆盖，
既不需要真的往用户回收站里塞东西，也不依赖环境是否支持回收站。

### 坑 15：PowerShell 会错误切分含点号的 `-D` 参数

**症状**：`mvn test -Dfilepanel.recycle.test=true` 报
`Unknown lifecycle phase ".recycle.test=true"`；
`java -Dfile.encoding=UTF-8 Foo.java` 报 `ClassNotFoundException: /encoding=UTF-8`。

**根因**：PowerShell 把 `-Dfilepanel.recycle.test=true` 在第一个点号处切开，
原生命令收到的是两段。跟批处理、跟 Maven 都没关系。

**规避**：从 PowerShell 调用原生程序时，含点号的 `-D` 参数必须加引号：
```powershell
& mvn.cmd test "-Dfilepanel.recycle.test=true"
& java.exe "-Dfile.encoding=UTF-8" -cp ...
```

## M4 最近使用 / 收藏标签 / 索引缓存（2026-09-20）

### 坑 17：星标列显示成一排「…」（**第一反应猜错了**）

**症状**：星标列里不是星号，而是一排"…"；表头的"★"却正常。

**我的第一反应**：字体缺字形（`☆` U+2606 渲染不出来）。
差点就去换字形了。

**真相**：把那一小块**裁剪放大**之后一眼就看清了——
列宽 34px，减去单元格默认的 8px×2 内边距、再减去星标自身的 4px×2，
留给文字的只有约 10px，装不下 15px 的星号，于是 **JavaFX 用省略号替换了文字**。

**规避**：
1. 星标列的单元格清掉默认内边距（`.star-column-cell { -fx-padding: 0; }`）
2. 给 Label 设 `setMinWidth(USE_PREF_SIZE)`，声明"最小宽度就是首选宽度"
3. 列宽 34 → 44px
4. 两种状态改用**同一个实心星号**，只用颜色区分——
   顺带也避免了"未收藏的字形在某些字体下太细"的问题

**教训**：**先放大看清楚再动手。** 1300px 宽的截图里 34px 的列只有几个像素，
"看起来像缺字形"和"看起来像省略号"在缩略图里无法区分。
为此写了个一次性的裁剪放大工具 `scratch/CropPng.java`（最近邻放大，像素边界清晰）。

### 坑 18：时间列被截断成 `2026-09-20 15:...`

**症状**：截图里两列时间全都以"…"结尾。**截断的时间戳等于没有信息**——用户既不知道具体时间，
也不知道被截掉的是分还是秒。

**规避**：列宽 125 → 148px（"2026-09-20 15:33"共 16 字符所需宽度），

### 坑 19：加了缓存之后，`lastResult != null` 不再是"扫描已完成"

**症状**：自检报"未收到任何进度回调"。而功能本身完全正常。

**根因**：索引缓存在**构造函数里**就把 `lastResult` 填上了，
于是自检的"等 `lastResult != null`"条件立刻满足，
它在后台扫描还没跑完时就继续往下读状态，读到的是半成品。

**这是我自己埋的坑**：`lastResult != null` 曾经等价于"扫描完成"，加了缓存后语义变了，
而所有依赖这个等价关系的地方（自检、截图模式）都在静默地变得不可靠。

**规避**：加显式的 `scanCompletions` 计数器作为"扫描完成"的唯一信号，自检与截图都改用它。
`showingCachedResult` 与 `cacheUsedAtStartup` 分开：前者用于状态栏提示（扫描完成后复位），
后者供自检判断"秒开有没有生效"（不复位）。

### 坑 20：同一毫秒内的多次操作，排序结果不确定

**症状**：`最近使用`的顺序偶尔对不上——测试里连续记录 b、c 两个文件，
期望 c 在前，实际有时是 b 在前。

**根因**：`System.currentTimeMillis()` 只有毫秒精度，两次操作落在同一毫秒时时间戳完全相同，
排序退化成"看谁先被遍历到"。**这不是测试写法问题，而是真实的用户体验问题**：
快速连续操作几个文件时，列表顺序会莫名其妙。

**规避**：给记录加一个**单调递增的次序号** `seq`（加载时取已有最大值 +1，跨次启动也保持递增），
排序改为「时间倒序，同毫秒按次序号倒序」。

### 坑 21：索引缓存用了带缩进的 JSON

**症状**：112 条的 `index.json` 竟然有 61 KB。

**规避**：给 `JsonFileStore` 增加紧凑写入（不缩进），61 KB → 47 KB（约 420 字节/条）。
配置与收藏/标签保留缩进（人可能会去翻一眼，缩进便于排查），
索引是纯机器数据，缩进只有代价没有收益。

**并据此下调了缓存上限**：按 420 字节/条，5 万条约 21 MB，
解析并构造对象会吃掉"秒开"的大部分预算，加上填表与排序很可能超过 1 秒——
那"秒开"这个承诺就不成立了。上限从 5 万改为 **2 万条（约 8 MB）**，
超过就老老实实重新扫描。**宁可要一个名副其实的小缓存，也不要一个名不副实的大缓存。**

### 关于"怎么验证重启后数据还在"

自检只跑一次进程，做不到真正的重启。所以拆成两层：
- **单测**：写入后用**新实例**读取（`survivesRestart` 一类），证明数据真的落盘了
- **自检**：验证缓存与存储的**写入→读回→还愿**往返一致，且"秒开"确实生效

另外为了能**看到**星标与标签的真实渲染效果，新建了一个只含临时文件的演示文件夹，
直接写入它的三个 JSON 状态文件再截图——既不碰你的真实资料，又能看到真实数据下的界面。
（`scratch/demo-folder/`，已 gitignore）

## M5 批量重命名 + 撤销（2026-09-20）

### 坑 22：`ATOMIC_MOVE` 会**静默覆盖**目标文件（我以为它更安全）

**我是怎么发现的**：写了一个"刻意让第二阶段失败"的测试——
生成计划之后偷偷在目标位置创建一个占用文件，预期重命名会失败并回滚。
结果测试报 `expected: <false> but was: <true>`：**操作"成功"了**。

**根因**：`moveWithFallback` 优先用 `StandardCopyOption.ATOMIC_MOVE`。
它的规范写着"其他选项被忽略；若目标已存在，是否替换<b>由实现决定</b>"。
在 Windows 上实测的结果就是**直接替换**——那个"占用者"文件被静静删掉了。

**这意味着什么**：从"冲突检查"到"实际移动"之间有时间窗。只要有人（别的程序、
同步工具、另一台机器）在这期间于目标位置创建了文件，重命名就会把它抹掉。
**用户只想改个名字，不该有任何文件消失。**

**规避**：改用不带任何选项的 `Files.move`，它在目标存在时抛
`FileAlreadyExistsException`，配合显式的存在性检查，给出的是"失败"而不是"毁掉一个文件"。
`RenameService`（单文件重命名）也做了同样修正——那里同样用过 ATOMIC_MOVE。

**这条与直觉相反，值得记住**：凡是"要不要覆盖"取决于实现的地方，都不能用。

### 坑 23：回滚靠"目标存在"猜文件在哪，结果把**别人的文件**搬走了

**症状**：修完坑 22 之后，回滚测试仍然失败——`b.txt` 的内容变成了占用者的内容。

**根因**：回滚时我这样判断"我的文件现在在哪儿"：
```java
if (Files.exists(item.target()) && !Files.exists(item.original())) {
    move(item.target(), item.original());   // 以为自己的文件在 target 上
}
```
但 `target` 之所以存在，有可能是因为**那里本来就是别人的文件**（正是导致第二阶段失败的原因）。
于是回滚把占用者的文件搬到了 `b.txt`，而真正属于 `b.txt` 的内容还留在临时名里——
**一次回滚把两个文件都搞乱了，而且不抛任何异常。**

**规避**：不再猜测。执行过程里我们其实<b>确切知道</b>每个文件在哪：
- 阶段二<b>成功</b>的条目 → 文件在最终名上 → 从最终名搬回原名
- 阶段二<b>未处理或失败</b>的条目 → 文件仍停在临时名上 → 从临时名搬回原名

拆成 `rollbackFromTarget()` 与 `rollbackFromTemp()` 两个只管一种情况的函数，
判断依据从"文件存不存在"变成"我们的执行记录"。

### 坑 24：模板里写了 `{ext}` 时又补了一次扩展名

**症状**：模板 `{yyyy}{mm}{dd}-{name}.{ext}` 得到 `20260920-报告.docx.docx`。

**根因**：模板展开后我又统一追加了一次扩展名——而模板里已经包含它了。

**规避**：检测模板是否引用了 `{ext}`，是则把展开结果当作完整文件名，不再追加。
检测用正则而不是 `contains("{ext}")`，这样 `{ ext }` 这类带空格的写法也能识别。

### 关于"测试要刻意制造失败"

坑 22 与坑 23 有一个共同点：**只测成功路径永远发现不了它们**。
成功路径下 ATOMIC_MOVE 和普通 move 看不出区别，回滚逻辑更是压根不会执行。

所以本里程碑专门写了三个"逆着来"的测试：
1. 计划生成后再占住目标名 → 逼出第二阶段的失败
2. 源文件不存在 → 逼出第一阶段的失败
3. 没有可撤销记录时调用撤销 → 逼出边界情况

**建议的做法**：每写一段"出错时怎么办"的代码，就想一个能稳定触发它的场景。
如果那个场景造不出来，说明这段错误处理很可能永远不会被执行到——那它大概率是错的。

### 顺带：用可读的实录补充自动断言

单测是自动断言，但"文件到底还在不在、内容对不对"这件事，
一段能直接看到输出的实录更有说服力。所以写了 `scratch/BatchRenameDemo.java`，
在临时目录里真实跑一遍「互换 → 撤销 → 规则改名 + 存储迁移 → 目标被占用回滚」：

```
[初始] A.txt=这是A的内容  B.txt=这是B的内容
[互换] 成功=true A.txt=这是B的内容  B.txt=这是A的内容
[撤销] 成功=true A.txt=这是A的内容  B.txt=这是B的内容
[改名] 收藏是否跟着走=true  标签=[重要, 待评审]  最近记录=2026-报告 v2.docx
[回滚] 成功=false
       问题：「y.txt」→「p-y.txt」 在改名阶段失败：FileAlreadyExistsException
[回滚] x.txt=X的内容  y.txt=Y的内容
[回滚] 占用者未被牵连=被占用的目标
[回滚] 是否残留临时文件=false
```

## M6 UI 打磨 + 打包（里程碑交付，2026-09-20）

### 坑 25：表格默认是**单选**，所以我做的多选功能从未可达

**症状**：不是崩溃，也不是报错——而是**做好的功能根本触发不到**。
我在 M3 精心实现了"多选混删时弹出三选一确认"，在 M5 实现了批量重命名，
但用户按住 Ctrl 点第二行时，第一行会被取消选中。

**根因**：JavaFX 的 `TableView` 默认 `SelectionMode.SINGLE`。
我从来没有显式设置过它，也从来没验证过"能不能真的选中多行"——
因为我写的自检断言是 `selectedItems().size() == 1`，单选模式下它照样通过。

**规避**：显式 `setSelectionMode(MULTIPLE)`。

**教训**：**"功能实现了"和"功能能被触达"是两件事。**
一个依赖多选的功能，它的验收条件里必须包含"确实选中了两行以上"。

### 坑 26：打包后拿不到 JavaFX 版本号

**症状**：开发期自检能打印 `JavaFX：17.0.13（javafx-graphics-17.0.13-win.jar）`，
打包后同一行变成 `unknown`——而"载入的是哪个 JavaFX"正是免装 Java 分发最需要证明的事。

**根因**：我原来的探测靠"加载来源 jar 的文件名"。jlink 生成的运行时里，
JavaFX 是 `lib/modules`（jimage）里的模块，**没有 jar 文件名**；
而它的 module-info 与 MANIFEST 本来就不带版本号（M0 就确认过）。

**规避**：让 Maven 在构建期把版本写进 `build-info.properties`（资源过滤），运行时读回来。
现在打包产物的自检会输出：
```
JavaFX：17.0.13（构建时固定；运行时镜像模式无法在运行时读出版本）
运行时：…\FilePanel\runtime
```
第二行是更硬的证据：它直接证明用的是随包自带的运行时。

**顺带一提**：资源过滤只对 `build-info.properties` 生效。若整目录开启 filtering，
其他资源（CSS 等）的字节内容也会被改写，将来一旦有人在 CSS 里写了 `${...}` 就会被静默替换。

### 坑 27：自定义单元格里的 Label **不继承** `-fx-text-fill`

**症状**：深色主题下文件名几乎看不见——深灰字印在深色背景上。
切回浅色主题一切正常。

**根因**：M6 给名称列加了"类型色块"，于是把这一列换成了自定义 `TableCell`，
里面放的是 `Label`。而 JavaFX 的 `-fx-text-fill` **不会从 TableCell 继承到 graphic 里的 Label**，
所以那个 Label 用的是默认黑色。原来的 CSS 只写了
`.file-table .table-row-cell .table-cell { -fx-text-fill: -fp-text; }`，
它对单元格生效，对单元格里的 Label 无效。

**规避**：给 Label 一个自己的样式类并显式指定颜色（`.file-table .name-label`）。

**教训**：**换自定义单元格 = 失去默认样式继承。** 顺手把"两种主题都看一眼"变成固定动作——
这个 bug 只测浅色主题是发现不了的。

### 坑 28：列宽持久化让"改默认值"对老用户永远无效

**症状**：我在 M4 把时间列从 125px 加宽到 148px 以避免时间戳被截断，
但打包后的截图里时间戳**又是截断的**。

**根因**：查落盘的 `config.json` 才发现，里面存的还是旧的 125。
`applyColumns` 忠实地恢复了用户（其实是我测试时）保存的旧宽度——
**修复只对新用户生效，老用户永远拿到旧值**。

**规避**：引入 `UiState.layoutVersion`。保存时写入当前版本；
读取时若版本落后，则**只沿用列的显隐、宽度回到新默认值**。
以后改动任何默认列宽就把 `FileTable.LAYOUT_VERSION` 加一。

**教训**：持久化会让"改默认值"变成一次**数据迁移**问题，而不是改个常量。

### 坑 29：批处理 `if (...)` 块里的变量在**整块解析期**展开

**症状**：`package.cmd deploy` 报 `Deploying into ""`，目标路径是空的。

**根因**：`if /i "%~1"=="deploy" ( ... )` 这种块在**执行前整个被解析**，
块内 `%TARGET_DIR%` 在解析时就展开了，而 `TARGET_DIR` 是块的第一行才赋值的。

**规避**：改用 `if ... goto :deploy` 跳到标签处，彻底绕开块。比开延迟展开更简单。

### 坑 30：`jpackage` 的 `--java-options` 必须拆成两个参数

**症状**：`--java-options=-Dfile.encoding=UTF-8` 报"选项无效"。

**规避**：写成 `--java-options "-Dfile.encoding=UTF-8"`（两个 token）。
从 PowerShell 调 jpackage 还会额外踩到"含点号的 `-D` 参数被切开"的问题（见坑 15），
所以打包命令一律写在 `.cmd` 里而不是临时用 PowerShell 拼。

## M7 全文内容搜索（2026-09-20）

### 坑 31：把条目名转成小写之后，却拿大写的字面量去比 —— xlsx 的文字永远抽不到

**症状**：`.xlsx` 里明明写着"灰度发布"，搜 `content:灰度发布` 搜不到；而同一张表里的**数字**能搜到。
**不报错、不警告**，只是结果少了。

**根因**：`isTextBearingEntry` 第一行是 `String n = entryName.toLowerCase(...)`，
下面却写 `n.equals("xl/sharedStrings.xml")` —— 大写 `S` 永远不等于小写化的名字。
于是 Excel 的共享字符串表（真正的文字都在那里）被整条跳过，只剩工作表里的数值。

**规避**：字面量改小写（`"xl/sharedstrings.xml"`），并在**测试里直接构造真实的 xlsx 内部结构**
（`xl/sharedStrings.xml` + `xl/worksheets/sheet1.xml`）来断言"文字和数字都要能搜到"。

**教训**：一旦决定"统一小写再比较"，**所有**参与比较的字面量都必须跟着改。
这种错法最阴的地方是：它只让结果变少，不让任何东西变红。

### 坑 32：Java 字符串里写 `"\\\\s+"` 得到的是"字面反斜杠 + s"

**症状**：摘要列里的文字带着换行，单元格被撑成多行。

**根因**：想表达正则 `\s+`，Java 源码里应该写 `"\\s+"`。写成 `"\\\\s+"` 后正则引擎看到的是
`\\s+`，含义变成"一个真正的反斜杠后面跟一个或多个 s"，换行根本没被压平。

**规避**：改成 `"\\s+"`，并在注释里写清"注意是一个反斜杠"，避免下次又被"多一层转义更安全"的直觉带偏。

### 坑 33：把"为什么跳过"吞掉了

**症状**：测试断言二进制文件应报 `BINARY`，实际拿到 `EMPTY`。

**根因**：二进制探测的结论没有立刻返回，而是往下走到"抽出来的文本是空的 → EMPTY"。
用户看到的是"没有可索引的文字"，而真实原因是"这文件根本不是文本"。

**规避**：把二进制判定**内联进抽取主流程**并当场返回。**教训**：错误原因必须在产生它的那一刻
就返回；一旦让它继续流下去，后面任何一层都会用自己更笼统的原因把它覆盖掉。

### 坑 34：加密的 Office 文件**不是坏文件**

**症状**：在真实文件夹上跑 `--content-search`，2 个文件报
"不是有效的 docx 文件：zip END header not found"。

**根因**：设了打开密码的 docx/xlsx，Office 会把整个 ZIP **加密后再包进一个 OLE2 复合文档**。
它根本不是 ZIP，所以解压当然失败。但文件本身完好无损，只是需要密码。
那句报错会让人以为文件损坏、白折腾。

**规避**：新增 `hasOle2Header()`（魔数 `D0 CF 11 E0 A1 B1 1A E1`），命中就报
`Skip.OLE2`「已加密或旧版 Office 格式」。**注意**：这个魔数同时覆盖"加密的 OOXML"
与"旧版二进制 .doc/.xls"，两者都拿不到正文，但都必须与"文件真的坏了"区分开——
用户看到"已加密"会去输密码，看到"读取失败"只会以为文件损坏。
测试里同时断言"真实 docx（ZIP 头）不能被误判"与"路径不存在时必须安全返回 false"。

### 坑 35：**开发期与打包后扫出两个不同的数字**（197 vs 113）

**症状**：`scripts\_java.cmd --scan` 报 **197 个文件**，双击打包后的 exe 报 **113 个**。
差 84 个、39 MB。

**根因**：程序自身目录（`app\`、`runtime\`）的排除用的是 `jpackage.app-path` 推出的**精确路径**。
这个属性**只有 jpackage 生成的 exe 启动时才存在**；用 `_java.cmd` 从 `target\classes`
启动时它是空的，于是 `app\`（12 个 jar）与 `runtime\`（142 个文件）都被当成了"用户的文件"。

**后果不只是数字难看**：`--content-search` 会去索引 `runtime\legal\*.md` 这类 Java 许可说明，
把"程序家具"灌进全文索引（索引里凭空多出 31 个文件、15 万字符），而
"命令行验证出来的数字"和"用户看到的数字"对不上时，**验证本身就失去意义**。

**规避**：新增 `Exclusions.forRoot(root)` —— 根目录里**同时**存在 `FilePanel.exe`、`app\`、
`runtime\` 三者时，按精确路径排除后两者。三者缺一就不动（宁可少排除，
也不能因为用户恰好建了个叫 `app` 的目录就把他的文件藏起来）。
界面、`--scan`、`--content-search` 三处统一改用这个入口，实测两种启动方式都报 **113**。

**教训**：凡是"结果依赖于启动方式"的判定，都会在验证环节变成谎言。发现两个数字不一致时，
不要挑一个信，要找出它们为什么不一样。

### 坑 36：验证输出别写进 `target\`

**症状**：`mvn clean package` 报 `Failed to delete ...\target\cs-out2.txt`，整个构建失败。

**根因**：为了"不污染工程目录"，我把命令行输出重定向到了 `target\` 里；
而 `target\` 正是 `clean` 要删掉的目录，而那个文件正被重定向句柄占着。
`clean` 删不掉就中止构建，于是 `target\filepanel.jar` 也没了，后续运行再报"找不到 jar"。

**规避**：验证产物一律写 `scratch\`（已在 `.gitignore` 里）。**教训**："临时目录"要选一个
**不会被构建过程清理**的地方，`target\` 恰恰是最不该放长期句柄的地方。

### 坑 37：自检写真实索引时不能"边写边读"

`ContentIndex` 是普通的 `LinkedHashMap` 包装，**不是线程安全的**。界面在用户输入
`content:` 后会启动后台 `ContentIndexer`；如果验证代码此时去读同一个索引，
就可能读到线程正在改的 map（极端情况下抛 `ConcurrentModificationException`，
更多时候是"命中数偶尔不对"这种查不出来的抖动）。

**规避**：自检在断言前**先等后台索引跑完**（`contentIndexer.isRunning()` 轮询，上限 30 s）。
截图模式同样要等——否则截到的是"0 命中 + 空摘要列"，看起来像功能坏了。

### 坑 38：把"已是最新"和"读取失败"混报成"跳过 N 个"

**症状**：状态栏写「内容索引完成：新索引 0 个文件，跳过 73 个」。
用户读到的意思是"73 个文件出错了"。

**根因**：`ContentIndexer` 里"指纹没变、直接复用"与"抽取失败"共用了一个 `skipped` 计数器。

**规避**：拆成 `upToDate`（好事，说明增量生效）与 `failed`（需关注）两个计数。
现在状态栏写「新索引 0 个文件，已是最新 71 个，无法读取正文 2 个」——
哪个是正常、哪个要处理，一眼就能分清。

## M3 补：删除阈值可配置 + "用调小阈值验证永久删除"（2026-09-20）

### 背景：一个"可配置"却没有入口的设置

D4 写的是"阈值默认 1 GB 且可配置"。实际上 `withThreshold()`、`DeletePolicy(long, boolean)`
与 `PRESET_THRESHOLDS` **只有定义、没有任何调用者**；`MainWindow` 里是写死的
`new DeletePolicy()`；`UiState`（落盘的配置）里也没有阈值字段。
也就是说这一项**只完成了代码层**，用户连一个能改的入口都没有。

这件事和"验证 ≥ 阈值分支需要造 1 GB 文件"是**同一个问题的两面**：
阈值一旦可配，把阈值调小就能用一个小文件走完同一条分支。

### 坑 39：`cmd /c "... & echo %ERRORLEVEL%"` 里的 `%ERRORLEVEL%` 是**解析期展开**的

**症状**：我用这个写法读了一整轮的退出码，全是 `0`——包括本该非零的情况。
发现它不可信，是因为测"未知参数应报错退出"时它依然报 0。

**根因**：`%VAR%` 在**整条命令被解析时**就展开了，`& echo` 里的 `%ERRORLEVEL%`
拿到的是 cmd 启动时的初值（0），跟前面那条命令的结果毫无关系。
（这正是坑 29 那个"批处理块在解析期展开"的同一个机制，只是换了层皮。）

**规避**：换成 `cmd /c "... > 文件 2>&1"` 然后用 `$LASTEXITCODE`。
并且**先用一个已知非零的对照组验证这个读法本身是准的**：

| 命令 | 期望 | 实测 |
|---|---|---|
| `cmd /c "exit /b 7"` | 7 | 7 ✅ |
| `FilePanel.exe --delete-tests x`（未知参数） | 2 | 2 ✅ |
| `FilePanel.exe --delete-test <不存在>` | 1 | 1 ✅ |
| `FilePanel.exe --scan` | 0 | 0 ✅ |

**教训**：一个"永远返回成功"的读数比没有读数更危险——它会让你以为一切都好。
换测量手段时必须先验它自身。

### 坑 40：拼错的命令行参数被静默忽略，程序转去打开图形界面

**症状**：我把 `--delete-test` 打成 `--delete-tests`，命令**挂了 5 分钟不返回**，最后超时被杀。

**根因**：`CliOptions.parse` 对不认识的参数一律忽略。参数被吞掉后，程序认为"没有任何命令"，
于是 `launch()` 打开图形界面——一个 GUI 进程，命令行调用方永远等不到它退出。

**规避**：把不认识的 `--xxx` 记进 `unknownOptions`，在主入口**报错 + 打印帮助 + `exit 2`**，
绝不落到图形界面。单测同时断言"认识的选项不会被误报"（避免把可用参数也拦掉）。

### 坑 41：部署脚本**先删后拷**，文件被占用时把可用的安装删坏了

**症状**：`package.cmd deploy` 失败后，原本能用的 `FilePanel.exe` 变成
`Error opening "…\app\FilePanel.cfg" file: No such file or directory`。**产品被自己的部署脚本毁掉。**

**根因**：脚本第 132 行先 `rmdir /s /q app` 和 `runtime`，再 `xcopy`。
一个正在运行的实例（或任何还持有 `app\*.jar`、`runtime\bin\*.dll` 的进程）会让
`rmdir` 删一半、`xcopy` 拷一半——旧版本没了，新版本不完整。

**规避**：改成"**先暂存、再改名让位、校验通过后才替换**"：
1. 先把新镜像完整拷到 `<目标>\.filepanel-deploy`，并校验 `FilePanel.cfg`/jar/`runtime\lib\modules` 都在；
2. 再用 **`ren app app.old`** 把旧目录移到一边（**改名失败 = 有文件被占用，此时什么都没动**）；
3. 拷贝新镜像并校验，全通过才删掉 `*.old`；
4. 任何一步失败都**把旧目录改名还原**，并明确告知"上一版已恢复"。

**教训**：一个会覆盖用户环境的脚本，绝不能"先破坏再重建"。
要么能回滚，要么在动手之前就把所有会失败的事都做完。

### 坑 42：`goto :label` 在**裸 LF** 的 .cmd 里会报 "cannot find the batch label"

**症状**：部署失败时应该跳去 `:swapFailed` 打印提示，实际报
`The system cannot find the batch label specified - swapFailed`，
而同一个文件里 `goto :deploy` 却一直正常。

**根因**：这个工程里**所有 .cmd 都是裸 LF 换行**（`CRLF=0 裸LF=197`）。
cmd.exe 是按行解析批处理的，简单语句能容忍 LF，但**标签查找不可靠**——
所以出现"有的 `goto` 能用、有的不能"这种最费解的表现。
另外：本项目用的是会写 LF 的编辑工具，**每编辑一次 .cmd 就会往 CRLF 文件里掺进裸 LF**。

**规避**：所有 `.cmd` 统一转成 CRLF（同时校验仍为纯 ASCII），
并把"编辑 .cmd 之后必须重新归一化"当作固定动作。检测与转换：

```powershell
$text=[IO.File]::ReadAllText($f) -replace "`r`n","`n" -replace "`r","`n" -replace "`n","`r`n"
[IO.File]::WriteAllText($f,$text,(New-Object Text.ASCIIEncoding))
```

### 坑 43：`tasklist` 在受限环境下返回 "Access denied"，守卫形同虚设

**症状**：我给部署脚本加的"运行中就拒绝部署"守卫用的是
`tasklist /FI "IMAGENAME eq FilePanel.exe" | find ...`。
实测它**根本没触发**，部署照样往下跑。

**根因**：这个环境里 `tasklist` 直接返回 **`ERROR: Access denied`**（进程枚举被限制），
输出为空 → `find` 找不到 → 判定为"没有在运行"。
**一个在受限环境下静默失效的守卫，比没有守卫更糟**——你会以为它挡住了。

**规避**：换成用**真实条件**做探测——**试着把 `app` 目录改名**。
Windows 不允许改名一个含打开文件的目录，而正在运行的实例必然持有 `app\*.jar`
与 `runtime\bin\*.dll`，所以"改名成功"就等价于"没有实例在运行"。
这个探测**不依赖任何进程列表**，而且**本身不破坏数据**（改名失败就等于什么都没发生），
实测：实例运行时 `guardExit=1` 且安装分毫未动。

### 坑 44：这一轮我自己写错的测试（被自检抓住的）

- `defaultThresholdIsOneGibAsLong`：断言写反了——期望 3 GiB 文件在 2 GiB 阈值下是 `RECYCLE`，
  实际（正确地）是 `PERMANENT`。**期望值抄错，不是产品错。**
- `rejectsOverflow`：我拿 `999999999 GB`（≈1.07e18 字节）去测"溢出保护"，
  但它其实仍在 `long` 范围内，属于合法输入。真正越界要 `9999999999 GB`。
- **更有价值的一次**：我加了"混合选择必须判为混合"的断言后重跑自检，
  它报"改设置后执行器实际使用的阈值：1073741824（应为 1048576）"——
  查下去发现是我自己上一步的编辑**把 `applyDeletePolicy(...)` 那一行注释掉了**
  （前一次编辑删掉了一个换行，把它并进了上一行的 `//` 注释里）。
  产品代码被验证抓回来——这正是"三段接线都要断言"的价值。

**教训**：测试写错和产品写错一样常见。区别在于——**断言写得足够具体时，
它会把两者都抓出来**；而只断言"没抛异常"的测试，两种错都抓不到。

## M10 搜索完善 + 批量创建（2026-09-20）

### 设计要点：范围只作用于"裸关键词"，显式语法永远优先

这一条不是顺手加的规则，而是决定这个功能是帮手还是陷阱的分界。
使用者常把整条复杂查询粘进搜索框（同事发来的一串条件、自己上次的查询）。
如果切换范围会让 `size:>10MB` 这类语法静默失效，用户看到的结果会莫名其妙地不对，
而他完全没有线索——因为界面上什么都没变。

所以实现上做了一次分流（`SearchParser.parseWithNotes`）：
只有被解析成"普通文字"的词才拿去按范围重新解释，凡是带显式语法的词一律原样保留。

### 坑 46：非法名字会把**整份计划**炸掉（`Path.resolve` 抛异常）

**症状**：单测 `planMarksIllegalEntries` 直接抛异常：
`InvalidPathException: Illegal char <|> at index 1: 含|竖线001`，
抛出位置是 `BatchCreatePlan.build`。

**根因**：我先 `targetDir.resolve(wanted)` 拼路径，再去 `validateName(wanted)` 验名字。
而 `Path.resolve` 碰到 `< > |` 这些字符**当场抛异常**。于是一个"某一项名字不合法"的小问题，
升级成了"整份计划生成不出来"——在界面上表现为点一下「批量创建」就崩。

**规避**：调换顺序——**先验名字，再拼路径**，并且把 `resolve` 也包进 try/catch 兜底。
（回头看，`BatchRenamePlan` 第 150 行本来就有这道 try/catch，我照抄结构时把最关键的一行漏了。）

**教训**：凡是"用户输入会参与拼路径"的地方，都要假设它会抛异常。
并且**校验必须在校验对象被使用之前**——顺序颠倒时错误信息会指向完全无关的地方。

### 坑 47：警告阈值按**数量**定，会出现自相矛盾的提示

**症状**：自检输出「数量 300 → 提示=数量较多：预计不到 1 秒」。
一边说"较多"，一边说"不到 1 秒"——这种提示用户看一眼就不信了，之后所有警告都会被无视。

**根因**：`WARN_COUNT = 200`、`STRONG_WARN_COUNT = 2000` 是拍脑袋定的数字，
而实测单条只要 0.7 ms（创建 + 重新扫描），200 项连 0.2 秒都不到。

**规避**：阈值改成按**预计耗时**定义——

```java
public static final long WARN_MILLIS = 1_000;        // 超 1 秒才提示
public static final long STRONG_WARN_MILLIS = 5_000; // 超 5 秒才要二次确认
public static final int WARN_COUNT =               // 数量阈值由时间反推
        (int) Math.ceil(WARN_MILLIS / (MILLIS_PER_CREATE + MILLIS_PER_RESCAN));
```

于是"有警告"必然等价于"真的要等一会儿"。单测里加了一条不变式扫描
（10/100/500/1000/5000/20000 项），断言 `warningLevel() > 0` 与
`estimatedMillis() > WARN_MILLIS` 永远一致。

### 坑 48：静态初始化里的**非法前向引用**

**症状**：编译报 `非法前向引用`，位置在 `WARN_COUNT` 的定义行。

**根因**：`WARN_COUNT` 用 `MILLIS_PER_CREATE` 算出来，而我把这两个耗时常量写在了它**下面**。
Java 不允许静态初始化里用简单名引用后面声明的字段。

**规避**：把派生常量挪到被依赖常量之后，并在注释里写明"必须声明在它们之后"，
免得下次整理文件顺序时又被绊一次。

### 坑 49：`Spinner.setValue(int)` 挑不到重载

**症状**：`countSpinner.setValue(Math.max(1, ...))` 报"找不到符号: 方法 setValue(int)"，
而同一个文件里 `startSpinner.getValueFactory().setValue(...)` 完全正常。

**规避**：统一用 `getValueFactory().setValue(...)`。它在泛型推断下没有歧义，
读起来也更明确（"改的是值工厂里的值"）。

### 坑 50：自检里的预览切片写错，导致"AA 没出现"（测试写错的第 N 次）

**症状**：自检报「字母递增到第 27 项应进位成 AA，实际预览：· 灰度发布检测点A_压力.docx」。

**根因**：预览只列**前 5 个 + 最后 1 个**。我为了看进位设了 `count=28`，
于是最后一项是第 28 项（`AB`），第 27 项（`AA`）根本不在预览里。
断言的目标项与预览的取样范围对不上。

**规避**：`count=27`，让进位那项正好落在"最后一项"的位置上，并在注释里写清这个约束。

**同一个坑在这一轮还出现了一次**：我断言"超过上限必须直接拒绝"，
但数量输入框是 `Spinner(1, MAX_COUNT, 10)`——**上限焊死在控件上，根本填不进去**，
所以"超限"这个状态在界面上不可达。产品的保护比我的断言更强，
断言却写成了"填进去再报错"。改成断言"尝试填 50001，实际被限成 50000"。

**教训**：断言之前先问一句"我这个断言走的路径，在真实界面上真的走得通吗"。

### 坑 51：下拉框里冒出 `FOLDER` / `NUMBER` / `SKIP`（**只有真的打开对话框才看得见**）

**症状**：用户在批量创建对话框里看到三个下拉框显示英文枚举名，而旁边的标签、"将新建 10 项"、
"预计不到 1 秒"全是中文——一眼就能看出是漏了转换。

**根因**：`ComboBox<T>` 默认显示 `T.toString()`，而枚举的 `toString()` 就是枚举名。
我在 `CreateRules` 里给这三个枚举都写了 `label()`（中文），但**没有谁去用它**：
`SearchBar` 那边我给 `SearchQuery.Op` 设过 `StringConverter`，这里三个都漏了。

**这类问题的可怕之处**：271 个单元测试 + 界面自检**全是绿的**。
因为"下拉框显示什么"既不是逻辑也不是数据，它只在界面被真正画出来的那一刻才存在。
我是靠用户发来的一张截图才发现的。

**规避**（两层，缺一不可）：

1. **从根上改**：给三个枚举覆盖 `toString()` 返回 `label()`。
   这样<b>任何</b>新加的下拉框默认就是中文，不需要每个使用处都记得设转换器——
   而"记得每个地方都设一遍"正是这次失败的原因。
2. **加一条能变红的断言**：遍历这几个枚举的全部取值，断言
   `toString() != name()` 且**至少含一个非 ASCII 字符**，再把具体文案钉住
   （`文件夹` / `数字 1,2,3` / `已存在就跳过`）。

**另外补了一个证据工具**：新增 `--create-preview <png>`，只把这个面板渲染成图片。
理由和当初做 `--settings-preview`、`--screenshot` 完全一样——
<b>有一类缺陷只能"看"出来，测不出来</b>。界面类改动的验收里，截图不是装饰，是唯一的证据。

### 提示词要能看出"位置"，而不是给个例子

**症状（同一个对话框）**：前缀/关键词/后缀三个框的提示原来是"例如 灰度发布""例如 检测点"
"例如 _压力"。看着挺具体，但回答不了用户真正的问题：**我填的这些东西会出现在名字的哪一段？**

**改法（用户直接给的方案）**：提示词改成**位置示意**——
前缀 `XXX记录`、关键词 `......记录......`、后缀 `记录XXX`，
再补一行「名字拼成的顺序：前缀 → 关键词 → 序号 → 后缀 → 扩展名」。

**为什么这比写说明文字好**：说明文字要用户先读、再记、再对应到三个框上；
位置示意是**看一眼就懂**，因为它把"这段在名字里的位置"直接画在了那个框里。

**教训**：多个输入框按顺序拼成一个结果时，"顺序"是最容易出错也最难用文字说清的信息，
应该尽量用预览或位置示意来表达，而不是加一段说明。

### 坑 52：刷新便携包时**把使用说明弄丢了**（而且文档还写着"包含说明"）

**症状**：用户问"还有没完成的任务吗"，我顺手核对压缩包内容，发现里面**没有 `使用说明.txt`**——
只有 exe / ico / app / runtime。而本节文档上写着"里只有可运行的四样东西 + 一份说明"。

**根因**：第一次打包时，说明文件是我**临时写进暂存目录**的。后来每次"刷新便携包"的脚本都是
`删除暂存目录 → 新建 → 只复制 exe/ico/app/runtime`——**说明文件的来源从来没被复制进去过**，
它只存在于第一次那个已经被删掉的暂存目录里。于是后面几版包全都缺说明，
而**没有任何一步会报错**：`Compress-Archive` 成功、包能解压、程序能跑。

**规避**：
1. 说明文件搬到仓库里当**唯一来源**：`FilePanel\docs\便携版使用说明.txt`，
   刷新包时从它复制。放进 `docs\` 而不是临时目录，是因为它属于"要被交付的产物"，
   不该存在于一个每次都会重建的目录里。
2. 打包后**核对包内顶层条目**（这次就是靠这一步发现的），而不是只看"压缩成功"。

**教训**：凡是"删掉重建"的流程，都要检查**每一个输入是不是都有稳定来源**。
这次的失败模式特别隐蔽：产物看起来完全正常，少的只是一份"不起眼"的文档。

### 坑 53：编辑 Markdown 时反复把**相邻标题吃掉**

**症状**：两次出现标题与正文并成一行（`### M8 缩略图与系统图标 ⏸ 暂缓（用户…决定）- 图片缩略图…`），
以及"便携版打包"这个 `##` 标题被整段替换掉、正文成了上一节的内容。

**根因**：我用"整块字面替换"来插入新章节，而 `old_string` 里包含了**下一个章节的标题**
（拿它当锚点是为了保证唯一匹配），`new_string` 里却忘了把它写回去。

**规避**：锚点要么选**不会被我改动的内容**（正文里的句子），要么在 `new_string` 里
**逐字保留**被用作锚点的那个标题。改完用正则扫一遍
`^#{2,4} .+ - ` 之类的畸形行来兜底。

**教训**：文档没有编译器。代码里吃掉一行会编译报错，Markdown 里吃掉一个标题
只会让内容悄悄跑偏——所以要靠"改完扫一遍结构"来代替编译器的角色。

## M8 缩略图与系统图标（2026-09-21）

### 坑 54：`GetIconInfo` 在 **user32** 而不是 gdi32

**症状**：`--icon-sheet` 直接抛
`UnsatisfiedLinkError: Error looking up function 'GetIconInfo': 找不到指定的程序。`

**根因**：函数名看着完全像 GDI 的东西（图标、位图），我就把它声明在了 `gdi32` 上。实际它在 **user32**。
**这类错误编译期完全看不出来**——JNA 是运行时按名字查符号，写错库只会在真正调用的那一刻炸。

**规避**：声明挪到 `User32Ex`，并在注释里点名"注意它在 user32 而不是 gdi32"，让下一个人不必再踩一次。

### 坑 55：PoC 抛异常把整条命令打死——**而这个函数表格每行都会调**

**症状**：上面那个 `UnsatisfiedLinkError` 没被降级处理掉，而是直接冒到 `main`，把整个 `--icon-sheet` 结束掉了。

**根因**：`extract()` 里没包异常。更严重的是**同一个函数会被表格每一行调用**——
如果这种异常发生在渲染路径上，用户看到的是列表直接坏掉，而不是"没有图标"。

**规避**：整个提取过程包进 `try/catch (Throwable)`，任何失败（DLL 少符号、结构体异常、被安全软件拦住）
都变成"这张图标取不到"，交给三级降级。

**教训**：**给界面用的底层函数，必须假设它随时会失败**，而且失败必须是一种正常返回值，而不是异常。

### 坑 56：用"首个像素"判断两张图标是否相同 → 必然相同

**症状**：自检报"docx 与 exe 的图标首个像素相同，怀疑所有扩展名拿到了同一张图"，
可图集里两张图标明明完全不同。

**根因**：图标**四角透明**，所以 `(0,0)` 对任何图标都是 `0x00000000`。
拿一个"必然相同"的位置去判断"是否相同"，等于断言写反了。

**规避**：改成**逐像素整图比对**（48×48 = 2304 次比较，代价可忽略），并把这个坑写进注释——
它是"看起来合理的断言其实恒真"的典型样本。

### 坑 57：静态方法里的匿名类拿不到实例字段（`nameColumn()` 是 `static`）

**症状**：编译报"无法从静态上下文中引用非静态 变量 icons"。

**根因**：名称列的单元格工厂定义在 `private static TableColumn<...> nameColumn()` 里，
匿名 `TableCell` 想直接用 `FileTable` 的实例字段 `icons`，而静态上下文里没有 `this`。

**规避**：在 `updateItem` 里从表格反查：`getTableView() instanceof FileTable t ? t.icons() : null`。
这比"把字段捕获进闭包"更好——`setIcons()` 可能在本表构造**之后**才调用，运行时反查才拿得到最新值。

### 坑 58：把 surefire 的 `Tests run` 当成"通过数"（**数字口径错误**）

**症状**：我在计划文档与实施笔记里连续几轮写"270 个通过""271 个通过"，都是从
`Tests run: 271, Failures: 0, Errors: 0, Skipped: 2` 这行"减去跳过数"得来的，但减错了——
**`Tests run` 本身已经包含 skipped**，正确是 271−2=269。

**根因**：拿到一个数字就直接做算术，没有回到那个数字的定义上去。

**规避**：
1. 引用测试数字时**照抄带单位的口径**（`Tests run: 278，其中跳过 2 → 实际通过 276`），
   而不是写一个自己算过的"通过数"。
2. 交叉核对：`src\test` 里 `@Test` 计数（实测 278）+ `@ParameterizedTest`/`@RepeatedTest`（0）
   应当能解释 `Tests run`。
3. 顺带修正一条**相关的事实错误**：那 2 个跳过的测试**不是**"需要管理员权限"，而是
   `@EnabledOnOs(WINDOWS)` + `@EnabledIfSystemProperty("filepanel.recycle.test"=true)` 的**显式开关**
   （它会真的往回收站写文件）。这个错误说法我写在三处文档里，已全部改正。

**教训**：本项目里第 N 次"我的数字/断言本身是错的"。所以现在有一条硬要求：
**每个写进文档的数字都要能指出来源（哪条命令、哪个文件），算过的数字要写清算式。**

## M9 收尾（2026-09-21）

### 坑 60：jpackage 嵌进 `.exe` 的图标**管不到窗口**

**症状**：资源管理器里 exe 图标是对的，但程序打开后**标题栏与任务栏是 JavaFX 的默认图标**。

**根因**：这是两个独立的图标。`.exe` 的图标是 jpackage 在打包时嵌进 PE 资源的；
窗口图标来自 `Stage.getIcons()`，**不设就是 JavaFX 默认值**。

**规避**：新增 `ui\AppIcons`，从 jar 资源里加载 16/32/48/256 四档 PNG 并 `stage.getIcons().addAll(...)`。

两个必须知道的细节：
1. **不能用 `.ico`**：JavaFX 的 `Image` 只认 png/jpg/gif/bmp，不认 ICO。`.ico` 只能给 jpackage。
2. **要放多个尺寸**，不能只放一张 256。标题栏图标实际是 16×16（高 DPI 下 32×32），
   让系统从 256 现场缩放会发糊。

**验证上的诚实说明**：标题栏**无法**用 `Scene.snapshot` 截到（它不属于场景内容），
所以自检能证明的只有"资源在 jar 里、每档都能解码、尺寸正确、且已加到窗口的图标列表里"，
**看起来对不对只能由人看窗口**。这一点写进了自检输出的注释里——
**不要为了凑一个"已验证"而声称截图证明了它**。

### 坑 61：修"没接上的清理逻辑"时，判定条件用错会把好数据也清掉

**背景**：`TagStore.pruneMissing(Predicate)` 写了实现却**零调用者**（同类问题见坑 62）。
接上它的时候有一个很容易走错的选择：**用什么判定"这个引用失效了"**。

**两个候选**：
- ❌ "这个路径**没有出现在本次扫描结果里**" —— 看着更"懂业务"，实则有害：
  被**排除规则**隐藏的文件（`.venv` 里的东西、`target\`、被 `app`/`runtime` 精确排除的程序自身）
  本来就不会出现在扫描结果里，它们会被当成"已删除"，**用户给这些文件打的标签会被无端清掉**。
- ✅ "这个路径**在磁盘上是否还存在**"（`Files::exists`）—— 只清真正消失的。

**规避**：用后者；放在**扫描完成之后的后台线程**里执行（此时既知道磁盘现状，也不占用界面线程）。
自检里两条断言都覆盖：造一条指向不存在路径的标签 → 必须被清掉；
再对**存在的**路径清一次 → **误清条数必须是 0**。

**教训**：写清理逻辑时，"失效"的定义要贴着**事实**（文件真的没了吗），
而不是贴着**当前视图**（它现在没显示出来）。视图会因为用户的筛选/排除设置而变，
事实不会。

### 坑 62：一个"读取本实例配置"的访问器返回了**静态常量**

**症状**：`Exclusions.filePatterns()` 返回的是静态的 `DEFAULT_FILE_PATTERNS`，
而同一个类里 `dirNames()` 返回的是实例字段。于是 `Exclusions.none()`（**明确表示"不排除任何东西"**）
经这个访问器会报出 **17 条文件规则**——**访问器在说谎**。

**为什么危险**：它现在没有调用者，所以不疼；但一旦将来"文件规则可配置"（界面上可增删），
测试、自检、设置界面都会读它，然后显示一份**与用户设置无关的默认规则**。
这类"没有调用者所以看起来无害"的错误最容易活到最坏的时刻。

**规避**：改成 `compiledFilePatterns()` / `compiledDirPatterns()`，返回**本实例**实际生效的规则
（类型也一并从 `List<String>` 改成 `List<Pattern>`——它本来就是编译后的），并加断言钉住：
`none()` 实例的两份规则都必须为空、`defaults()` 的文件规则条数必须与 `fileRuleCount()` 一致。

**顺带记一个我在写这条断言时犯的错**：我一开始断言
`dirRuleCount() == compiledDirPatterns().size()`，实际是 **34 vs 3** 而失败——
`dirRuleCount()` 是"31 条精确名 + 3 条通配符"之和，而 `compiledDirPatterns()` 只是其中通配符那部分。
**两个数字口径不同，长得像不等于含义相同**（同坑 58）。
## M11 安装包（2026-09-21）

### 坑 63：`jpackage --type msi` 是 WiX 的薄包装，而 WiX 不在 JDK 里

**症状**：`jpackage --type msi` 报 "WiX is required"（或直接找不到 candle.exe/light.exe）。
本机实测：`candle.exe`/`light.exe` 都没有，也没有任何 WiX 目录。

**根因**：jpackage 的 msi/exe 类型只负责**生成 .wxs 源文件**，真正把它编译链接成 MSI 的是
WiX Toolset 的 `candle.exe` + `light.exe`，那不是 JDK 的一部分。

**规避**：用 WiX 的**二进制 zip**（`wix314-binaries.zip`，39.4 MB）解压到 `tools\wix314\`，
再把该目录临时加进 PATH。**不要用 WiX 自己的 .exe 安装程序**：它要管理员权限、会写
Program Files；而 zip 只是解压，工具链就留在项目里，和 `tools\maven`、`tools\m2repo` 一个待遇。
下载脚本：`scripts\fetch-wix.mjs`（用 node，因为本环境 pwsh 没有网络）。

### 坑 64：jpackage **吞掉了 light.exe 的真实报错**，只留下一句"exited with 216 code"

**症状**：`jpackage --type msi` 失败，输出里唯一的线索是
`... exited with 216 code`，没有任何 WiX 的错误信息。而 216 这个数字本身查不出所以然。

**根因**：jpackage 调用外部工具时只汇报退出码，不把子进程的 stderr 转出来。

**规避**：给 jpackage 加 `--temp <目录>` **保住中间产物**，然后**自己按同样的参数跑一遍
light.exe**，就能看到真正的错误：

```
error LGHT0217 : Error executing ICE action 'ICE01'. ...
    "The Windows Installer Service could not be accessed."
error LGHT0216 : An unexpected Win32 exception with error code 0x643
```

根因是 **ICE 校验需要访问 Windows Installer API，而本环境访问不到**（与回收站
`C:\$Recycle.Bin` 写不进去是同一类限制）。ICE 校验只是对**已经构建好的 MSI** 做一遍
authoring 规则检查（lint），跳过它不改变产物内容——所以用 `-sice:ICE01…ICE300` 全部抑制后
让它把 MSI 写出来即可。注意 WiX 的编号既有 `ICE01` 也有 `ICE100`，**两种补零形式都要生成**，
"ICE1" 匹配不上 "ICE01"。

**教训**：外部工具失败但只给你一个退出码时，**先想办法把它的原始输出弄出来**，
不要在退出码上做猜测。

### 坑 65：我第一次"手工复现"时选错了语言文件，**造出三个假报错**

**症状**：手动跑 light.exe 得到
`error LGHT0102 : The localization variable !(loc.MainFeatureTitle) is unknown` 等三条，
看起来像是"jpackage 生成的中文语言文件缺键"，我差点顺着这个方向去改本地化文件。

**根因**：我用 `Get-ChildItem -Filter '*.wxl' | Select-Object -First 1` 取语言文件，
拿到的是**英文**那个（`MsiInstallerStrings_en.wxl`），却仍然按 jpackage 原样传了
`-cultures:zh-CN`。light.exe 于是去找 zh-CN 的字符串却只拿到 en 的，才报"变量未知"。
**中文那个文件里那三个键其实一个都不缺。**

**规避**：手工复现一个工具调用时，**参数要逐字对齐**，尤其是"哪个文件"这种由程序挑选的输入。
我后来改成按文件名匹配 `_zh_CN.wxl` 并让它与 `-cultures:zh-CN` 配套，报错才变成真因（坑 64）。

**教训**：**复现失败现象时，复现本身的正确性也要被质疑**。一个错误的复现会把你带向
一个根本不存在的 bug，而且它看起来非常有说服力（有具体的错误信息、有具体的文件）。

### 坑 66：PowerShell 数组字面量里，**逗号比 `+` 优先级高**

**症状**：`finish-msi.ps1` 报 `error LGHT0103 : The system cannot find the file 'zh-CN' with type 'Source'`。

**根因**：我写的是
```powershell
$arguments = @('-nologo', '-ext', 'WixUIExtension', '-cultures:' + $culture, '-out', $Out)
```
在数组字面量里**逗号先结合**，于是表达式成了 `'-cultures:' + @($culture, '-out', $Out, ...)`，
拼接结果被拆开，light.exe 收到了一个孤立的 `zh-CN`，把它当成源文件名。

**规避**：用**单个插值字符串**：`"-cultures:$culture"`。并把这个原因写进注释，
因为这种写法看起来完全正常。

### 坑 67：MSI **安装**必须往 `C:\Windows\Installer\` 写东西 —— 本环境装不了

**症状**：`msiexec /i FilePanel-1.0.0.msi /qn` 返回 **1603**。日志里的真因是：

```
DEBUG: Error 2503: Called RunScript when not marked in progress.
Note: 1: 2203  2: C:\Windows\Installer\inprogressinstallinfo.ipi  3: -2147287035
```

`-2147287035` 是拒绝访问：MSI 安装要在 `C:\Windows\Installer\` 写**回滚脚本**与
`inprogressinstallinfo.ipi`，而那个目录在工作区之外，被沙箱挡住。

**结论（重要的诚实声明）**：**"能造出 MSI"不等于"能装上"**。本环境只能证明前者。
所以 M11 的验收里，**安装 / 升级 / 卸载三项我明确标为"未在本环境验证"**，
并给出你在真机上要跑的三条命令与预期结果——**不把"生成了文件"说成"功能已验证"**。
这和当初回收站那件事是同一种处理：环境不允许的部分，如实标出来，交给真机。

### 坑 68：`build.cmd` 是 `clean package`，**会把 target\ 连同刚做好的安装包一起删掉**

**症状**：MSI 明明构建成功（45.5 MB），几分钟后去找却"文件不存在"。

**根因**：我在产出 MSI 之后又跑了一次 `scripts\build.cmd`（= `mvn clean package`），
`clean` 把整个 `target\` 删了，而 MSI 就在 `target\installer\` 里。

**规避**：
1. **安装包要在最后一次构建之后才生成**，或者生成后**立刻复制到 `target\` 之外**；
   `package.cmd installer` 现在会把它复制到工作区根目录（`FilePanel-安装版-<版本>.msi`）。
2. 这与坑 36（不要把验证输出重定向进 `target\`）是同一类问题的两种表现：
   **`target\` 是一个随时会被清空的目录，任何"要留下的东西"都不该只存在于那里。**

### 坑 45：程序会往用户目录写一个 3.4 MB 的 JavaFX 缓存（已如实告知，暂未修）

首次运行会在 `%USERPROFILE%\.openjfx\cache` 建约 **3.4 MB / 50 个文件**的原生库缓存。
原因：打包时没设 `-Djavafx.cachedir`，JavaFX 就用默认位置。

这**不影响**计划的验收项（§8「不污染」指的是"程序目录与数据目录不出现在自己的文件列表里"，
那一项是满足的），但确实往用户目录写了东西。

**这一轮刻意不改**：设置 `javafx.cachedir` 要靠 jpackage 的 `$APPDIR`/`$ROOTDIR` 变量替换，
而替换在 `--java-options` 里是否生效必须重新打包并实测才敢下结论。
为了 3.4 MB 的缓存去冒"启动器在用户机器上跑不起来"的风险不划算。
要修的话：先验证替换确实生效，再把缓存指到已经自动隐藏的 `app\` 下面。
