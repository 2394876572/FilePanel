## 1. 三十秒版本

```cmd
cd FilePanel
scripts\build.cmd                 :: 编译 + 跑测试 + 打 jar（必须成功才继续）
scripts\run.cmd                   :: 用开发方式启动界面（管的是项目上一级目录）
scripts\package.cmd               :: 生成自带 JRE 的 app-image（target\dist\FilePanel）
scripts\package.cmd deploy        :: 平铺部署到项目上一级目录，产出可直接双击的 exe
```

产物形态（平铺部署，**exe 就在被管理文件夹的顶层**）：

```
<目标文件夹>\FilePanel.exe      真正的 exe 入口（无控制台、带图标）
             FilePanel.ico
             app\               程序自身（jar + FilePanel.cfg）
             runtime\           自带 JRE（jlink 裁剪，含 JavaFX 模块）
             .filepanel\        数据目录（隐藏，运行时自动生成）
```

程序**按自己所在的位置**决定管理哪个文件夹，所以整份拷到哪台机器、哪个目录都一样。

## 2. 环境要求与两个必须知道的陷阱

| 项 | 值 |
|---|---|
| JDK | **必须 17+**。本机默认 `JAVA_HOME=C:\jdk-1.8`，**脚本内部已强制覆盖为 `C:\jdk17`** |
| Maven | 项目内 `tools\apache-maven-3.9.9`（没有本地仓库依赖的外部 Maven） |
| 本地仓库 | 项目内 `tools\m2repo`（**不是** `~\.m2`） |
| 语言级别 | `maven.compiler.release = 17` |
| 操作系统 | Windows（`win\` 包直接调 shell32/user32/gdi32，界面层依赖 JavaFX） |

### 陷阱 1：`JAVA_HOME` 指向 JDK 8 —— 绝不要"修正"它

JavaFX 17 需要 JDK 17。`scripts\mvn.cmd` 里硬编码了 `set "JAVA_HOME=C:\jdk17"`。
如果你在 IDE 或命令行里直接调 `mvn`，而环境变量指向 JDK 8，会得到一堆
`UnsupportedClassVersionError` 或 JavaFX 模块找不到的报错。**用脚本，不要绕过脚本。**

### 陷阱 2：`.cmd` 文件必须保持**纯 ASCII + CRLF**

- 脚本里有 `chcp 65001`。cmd.exe 按**字节偏移**跟踪自己在批处理文件里的位置，
  一旦文件里出现非 ASCII 字节，切到 UTF-8 后解析器会从一行中间继续执行，跑出莫名其妙的结果。
  **所以所有 `.cmd` 一律只写英文注释，中文注释放 `docs\`。**
- 另一个更隐蔽的问题：**`goto :label` 在裸 LF 换行的批处理里会报
  `cannot find the batch label`**，而同一个文件里别的 `goto` 却正常。
  用会写 LF 的编辑器改过 `.cmd` 之后，**必须重新归一化成 CRLF**：

```powershell
$f = "scripts\package.cmd"
$text = [IO.File]::ReadAllText($f) -replace "`r`n","`n" -replace "`r","`n" -replace "`n","`r`n"
[IO.File]::WriteAllText($f, $text, (New-Object Text.ASCIIEncoding))
```

**补充：`.ps1` 不受这条约束，但必须带 UTF-8 BOM。**
`scripts\demo-screenshots.ps1` 要写 14 个中文文件名和中文搜索词，那些字节放进 `.cmd` 会踩上面这个坑，
放进 `.ps1` 则没事——PowerShell 的脚本解析不按字节偏移跟踪位置。唯一的硬要求是
**文件必须以 UTF-8 BOM 开头**（`New-Object Text.UTF8Encoding($true)`）：Windows PowerShell 5.1
在没有 BOM 时按 ANSI 代码页读脚本，中文会变成乱码。`scripts\finish-msi.ps1` 同样是 BOM 开头。

## 3. 构建脚本逐个说明

| 脚本 | 作用 | 备注 |
|---|---|---|
| `scripts\mvn.cmd` | Maven 包装器：强制 `JAVA_HOME=C:\jdk17`、切 UTF-8 控制台、指定项目内 Maven 与仓库 | 其余脚本都通过它调用 Maven |
| `scripts\build.cmd` | `mvn clean package` —— 编译 + 跑测试 + 打 `target\filepanel.jar` + 复制依赖到 `target\app`、`target\javafx` | 三个产物目录正是 jpackage 需要的输入 |
| `scripts\_java.cmd` | 共用启动器：`--module-path target\javafx -cp target\filepanel.jar;target\app\*` | 各运行脚本都调它；**它用 `target\filepanel.jar`，所以改了代码必须先 build 才会有新行为** |
| `scripts\run.cmd` | 启动图形界面（开发方式） | 默认管项目上一级目录 |
| `scripts\scan.cmd` | `--scan`：无界面扫描，输出统计 | |
| `scripts\selftest.cmd` | `--selftest`：环境自检 | |
| `scripts\uiselftest.cmd` | `--ui-selftest`：界面链路自检（**最有用的一键验证**） | |
| `scripts\screenshot.cmd` | `--screenshot`：把界面渲染成 PNG | |
| `scripts\demo-screenshots.ps1` | **一键重拍 `docs\screenshots\` 里全部截图**（先造虚构示例文件夹，再逐张渲染） | 中文文件名只能写在 `.ps1` 里，见第 2 节陷阱 2 的补充 |
| `scripts\package.cmd` | 生成 app-image；`package.cmd deploy` 平铺部署 | 见第 5 节 |
| `scripts\fetch-maven.mjs` | 下载项目内 Maven 到 `tools\apache-maven-3.9.9` | 换机器时先跑它（需要网络） |

**注意**：`scripts\build.cmd` 是 `clean package`，会把 `target\` 整个删掉重建。
**不要把自己的验证输出写进 `target\`** —— 重定向句柄会占住文件导致 `clean` 删不掉、
整个构建失败（实测踩过）。

## 5. 打包与部署（`package.cmd`）

1. **jlink**：用 JDK 17 裁剪出一个只含所需模块的运行时（含 JavaFX），约 48.6 MB
2. **jpackage --type app-image**：把它们组装成 `target\dist\FilePanel\`
3. **deploy**：把 app-image 的**内容**铺进目标文件夹（平铺，不留 `FilePanel\` 子目录）

### deploy 的关键设计：先暂存 → 改名让位 → 校验 → 替换

老版本是"先 `rmdir` 旧目录再 `xcopy`"。结果：**只要有任何文件被占用，旧安装就被删一半、
新安装只拷了一半**，产品直接坏掉（实测发生两次，报 `Error opening app\FilePanel.cfg`）。
现在的流程是：

1. 先把新镜像完整拷到 `<目标>\.filepanel-deploy\` 并校验关键文件都在；
2. 再用 **`ren app app.old`** 把旧目录移到一边——
   **这一步同时充当"是否被占用"的检测**：Windows 不允许改名一个含打开文件的目录，
   而正在运行的实例必然持有 `app\*.jar` 与 `runtime\bin\*.dll`；
3. 拷贝新镜像并再次校验，全通过才删掉 `*.old`；
4. 任何一步失败都把旧目录**改名还原**，并明确告知"上一版已恢复"。

**为什么不用 `tasklist` 检测进程**：本项目的构建环境里 `tasklist` 直接返回
`ERROR: Access denied`（进程枚举被限制），守卫会**静默失效**——而一个悄悄不生效的守卫
比没有守卫更糟。改用"能否改名"这个真实条件后，实测实例运行时 `deploy` 被拒绝且安装分毫未动。

> 因此：**部署前请关掉正在运行的 FilePanel**。被拒绝不是 bug，是保护。

## 7. 数据与重置

所有状态都在**被管理文件夹**下的 `.filepanel\`（隐藏目录），不写注册表、不写 `AppData`：

| 文件 | 内容 |
|---|---|
| `config.json` | 窗口尺寸与位置、主题、排序列与列宽、是否显示文件夹、**删除阈值**、`alwaysRecycle`、**搜索范围** |
| `recent.json` | 最近打开过的文件 |
| `favorites.json` / `tags.json` | 收藏 / 标签 |
| `index.json` | 扫描索引缓存（用于秒开） |
| `content-index.json` | 全文索引（正文字符数有上限） |
| `delete-journal.json` | 删除日志（永久删除的标为不可恢复） |
| `rename-journal.json` | 批量重命名的撤销日志（保留最近若干批） |
| `create-journal.json` | 批量创建的撤销日志（**与重命名分开存**：撤销创建是删东西、撤销重命名是改名，混在一起会出大错） |

**重置办法**：删掉整个 `.filepanel\` 目录即可，下次启动全部重建为默认值。
所有 store 都继承 `JsonFileStore`，**读坏时回到默认值而不是崩溃**——这也是测试显式覆盖的行为。

## 8. 故障排查速查

| 现象 | 先看这里 |
|---|---|
| `UnsupportedClassVersionError` / JavaFX 模块找不到 | `JAVA_HOME` 是不是 JDK 8？用 `scripts\*.cmd` 而不是直接 `mvn` |
| `mvn clean` 报删不掉某个文件 | 你是不是把输出重定向到了 `target\` 里？改用 `scratch\` |
| 批处理报 `cannot find the batch label` | 该 `.cmd` 被编辑器改成裸 LF 了，重新归一化成 CRLF |
| `.cmd` 执行到一半跑出乱码命令 | 文件里混进了非 ASCII 字节（第 2 节陷阱 2） |
| `deploy` 报"the installed copy is in use" | 有 FilePanel 正在运行，关掉再部署。**这是保护，不是故障** |
| 部署后 exe 报 `Error opening app\FilePanel.cfg` | 安装不完整。重新 `package.cmd deploy`；若仍失败，看是否被占用 |
| 界面能出数据但看不见文件名（深色主题） | 单元格里 `Label` 需要自己的样式类，`-fx-text-fill` 不会从 `TableCell` 继承进 graphic |
| 表格行高/列宽突变、文字被截断 | 默认列宽改动需要同时提升 `FileTable.LAYOUT_VERSION`，否则老配置一直沿用旧宽度 |
| 搜索选中了范围却不生效 | 显式语法优先于范围（设计如此）；看搜索框右侧提示行确认实际生效的条件 |
| 系统图标全是色块 | 该机器上 `ShellIcons.available()==false`。用 `--icon-sheet` 看具体原因；这是允许的降级 |
| 图片没有缩略图 | 扩展名不在支持列表 / 文件超过 40 MB / 解码失败。都会静默降级为类型图标，不影响功能 |
| 删除大文件时界面卡住 | 已知问题：删除在 JavaFX 线程上同步执行，**回收站**那一侧耗时随体积线性增长。见第 9 节 |

## 9. 已知限制与未完成项

完整清单见 `..\文件面板-开发计划.md` 的 **§8.2 未完成清单**（含每条的状态与理由）。摘要：

1. **删除在 JavaFX 线程上同步执行**：走回收站的文件要把数据真的搬进 `C:\$Recycle.Bin`，
   一个 900 MB（阈值以下）的文件可能让界面卡几秒。永久删除那一侧无此问题
   （NTFS 上只是标记簇空闲，与体积无关）。正解是挪到后台线程 + 进度提示。
2. **JavaFX 缓存写在用户目录**：`%USERPROFILE%\.openjfx\cache` 约 3.4 MB（打包时没设
   `javafx.cachedir`）。要修得先验证 jpackage 的 `$APPDIR` 变量替换在 `--java-options` 里确实生效。
3. **`MainWindow.scan(Path)`（切换文件夹）绕过 `layoutVersion` 判断**：
   坑"默认列宽改动对老配置无效"的迁移在换根目录这条路上失效。
4. **`TagStore.pruneMissing` 没有调用者**：文件被外部删除后，孤儿标签不会被清理。
5. **`Exclusions.filePatterns()` 返回静态默认常量**（而 `dirNames()` 返回实例字段），API 不一致。
6. **批量创建的界面接线没有真的点过**：点按钮→对话框→后台线程→刷新→撤销按钮这串只由
   自检验证了对话框逻辑与按钮存在性；真实创建/撞名/撤销/单项失败由单测在临时目录里跑通。
7. **`--recycle-test` 没有单独跑过**（界面链路走同一个 `DeleteService`，已验证）。
8. 死代码若干：`Glob.matchesAny`、`JsonFileStore.wrap`、`CliOptions.isHeadlessMode`、
   若干只给自检用的访问器。

## 10. 验证纪律（这个项目最值得继承的一条）

代码里到处是"能返回一个看起来正常的数字，但结论是错的"这种失败方式。所以约定：

1. **界面类改动必须看图**。CSS 写错、下拉框漏转中文、图标方向颠倒——这些**单测与自检全绿**，
   只有把界面画出来才看得见。本项目就是靠截图发现过"深色主题下文件名看不见"、
   "批量创建下拉框显示 FOLDER/NUMBER/SKIP"。
2. **API 说成功不算成功**。`SHFileOperationW` 返回成功、文件也确实消失了，
   但回收站条目数没变——它其实被永久删除了。所以删除后会**另外查一次回收站条目数**再下结论。
3. **写进文档的每个数字都要能指出来源**（哪条命令、哪个文件）。算过的数字要写清算式：
   例如 surefire 的 `Tests run` **包含** skipped，`Tests run: 278, Skipped: 2` 的实际通过是 276，
   不是 278 也不是 277。
4. **失败原因必须说人话**。加密的 Office 文件不是"文件损坏"，是"已加密，读不了正文"；
   搜索语法没解析出来不是静默 0 结果，是"已按普通文字搜索"。用户看到的是原因，不是错误码。

`docs\实施笔记.md` 里有 **59 条**按编号记录的坑，每条都写了症状、根因、规避与教训，
按主题索引见 `架构与代码说明.md` 的最后一节。**改代码之前先扫一遍那份笔记**，
大概率你要碰的地方已经踩过了。
